OAuth2TokenValidator<Jwt> existingValidators =

我们用**同一枚 JWT** 走一遍退出登录。假设 `petcure_test02` 登录后拿到令牌 A。它能访问 `/api/users/me`，是因为后端能验证它的签名、有效期和身份。用户退出时，后端把 A 的编号写进 MySQL。此后，即使有人把 A 原样发回来，后端也会根据这条记录拒绝请求。

整个功能由两个动作配合完成。**`/logout` 负责写入撤销记录，JWT 校验器负责读取撤销记录。** 你已经在 Postman 和 Navicat 验证了写入这半条链路，后面也补上了读取的代码。

**1. 登录时，`JwtService` 已经给每枚令牌分配了编号**

还记得生成 JWT 时的这两行吗？

```
.subject(userId.toString())
.id(UUID.randomUUID().toString())
```

它们分别设置两个不同的字段：

| JWT 字段 | Java 读取方式      | 用途                                |
| -------- | ------------------ | ----------------------------------- |
| `sub`    | `jwt.getSubject()` | 用户 ID。`/me` 用它查当前用户       |
| `jti`    | `jwt.getId()`      | 令牌 ID。退出接口用它撤销这一枚令牌 |

同一个账号登录两次，两个令牌的 `sub` 一样，`jti` 各自不同。我们希望退出一次只影响这次登录，因此撤销表用 **`issuer + jti`** 定位令牌。`issuer` 来自 JWT 的 `iss`，表示签发者。

**2. 发送退出请求时，安全过滤链先确认这枚令牌可用**

在 Postman 里，你发送的是：

```
POST /api/auth/logout
Authorization: Bearer <令牌 A>
```

请求体留空。后端从请求头拿到 A，`SecurityConfig` 配置的安全过滤链调用 `JwtDecoder` 进行验证。退出接口走 `.anyRequest().authenticated()`，所以只有认证通过，请求才会进入 `AuthController.logout()`。

```
@PostMapping("/logout")
public ApiResponse<Void> logout(@AuthenticationPrincipal Jwt jwt) {
    authService.logout(jwt);
    return ApiResponse.success();
}
```

`@AuthenticationPrincipal` 注入的是**安全过滤链已经验证过的 `Jwt` 对象**。`AuthController` 直接把这个对象交给 `AuthService`。因此，客户端只需要发送令牌，服务端就知道这次要撤销哪一枚。

**3. `AuthService` 取出令牌信息，`JwtRevocationMapper` 写入 MySQL**

下面是 `AuthService.logout()` 里的关键代码。实际方法在时间转换前还检查了签发者、令牌编号和到期时间是否齐全。

```
Object issuer = jwt.getClaims().get(JwtClaimNames.ISS);
String jti = jwt.getId();

LocalDateTime expiresAt = LocalDateTime.ofInstant(
        jwt.getExpiresAt(),
        ZoneOffset.UTC
);

jwtRevocationMapper.insertRevocation(issuer.toString(), jti, expiresAt);
```

这就是刚才构造方法注入派上用场的地方。**`jwt` 来自这一次退出请求，`jwtRevocationMapper` 是 Spring 创建 `AuthService` 时就传入并保存在字段里的对象。** `logout()` 负责取数据，然后用这个 Mapper 执行写入。

`JwtRevocationMapper.insertRevocation()` 对应的 SQL 是：

```
INSERT INTO jwt_revocation (issuer, jti, expires_at, revoked_at)
VALUES (#{issuer}, #{jti}, #{expiresAt}, UTC_TIMESTAMP())
ON DUPLICATE KEY UPDATE revoked_at = jwt_revocation.revoked_at
```

前三个值来自 `AuthService`，`revoked_at` 由数据库填写。表中的 `expires_at` 是**令牌原本的到期时间**，`revoked_at` 是**用户提前退出的时间**。你在 Navicat 里看到 `revoked_at` 早于 `expires_at`，就是这个场景。

如果两次退出请求都已经通过认证并尝试写入同一枚令牌，主键和 `ON DUPLICATE KEY UPDATE` 会让表里只保留一条记录，并保留首次撤销时间。数据库操作正常返回后，`AuthController` 才返回 `200 SUCCESS`。

**4. 再拿令牌 A 访问 `/me`，`JwtConfig` 接入的校验代码会查撤销表**

这是**另一条 HTTP 请求**：

```
GET /api/users/me
Authorization: Bearer <同一枚令牌 A>
```

A 的内容没有变化，变化的是 MySQL 里已经多了一条撤销记录。`JwtDecoder` 先验签，再执行我们在 `JwtConfig` 里通过 `decoder.setJwtValidator(...)` 接入的校验。核心代码可以分成两段：

```
OAuth2TokenValidatorResult result = existingValidators.validate(jwt);
if (result.hasErrors()) {
    return result;
}
```

这一段保留原有规则，例如签发者、接收方和有效期。原有规则通过后，代码检查 `jti` 是否存在，然后用**与退出写入时相同的字段**查询：

```
String tokenIssuer = jwt.getClaims().get(JwtClaimNames.ISS).toString();

if (jwtRevocationMapper.countRevocations(tokenIssuer, jti) > 0) {
    return OAuth2TokenValidatorResult.failure(
            new OAuth2Error("invalid_token", "JWT 已撤销", null)
    );
}

return OAuth2TokenValidatorResult.success();
```

`countRevocations()` 执行的是 `WHERE issuer = #{issuer} AND jti = #{jti}`。对 A 来说，数据库能查到退出时写的那条记录，校验器就返回失败。`SecurityConfig` 配置的认证失败处理器会把它转换成 **HTTP 401 `UNAUTHORIZED`**，请求到这里结束，`UserController.me()` 和 `UserService` 都不会执行。如果换成同一账号另一枚仍有效、未撤销的令牌，它的 `jti` 不同，就能继续通过这项检查。

下次独立做这个功能时，可以从验收条件倒推代码。要让**同一枚未过期的令牌在退出前能访问、退出后被拒绝**，先在签发时给令牌一个唯一编号，再让退出接口持久化这个编号，最后在所有受保护请求共用的 JWT 校验入口检查它。这个顺序也解释了我们为什么先看到 `/logout` 返回 `200`，之后才去修改 `JwtConfig`。前者验证的是**撤销记录能写进去**，后者决定这条记录能不能**阻止下一次请求**。
